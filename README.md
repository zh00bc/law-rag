## 架构原理

```
用户提问
  │
  ▼
┌──────────────────────────────────────────────┐
│  OpenClaw Agent                               │
│  识别为税法问题 → 调用 exec 工具              │
└──────────────┬───────────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────┐
│  query.py — 混合检索                          │
│                                               │
│  1. Embedding API 将问题转为 1536 维向量       │
│  2. 语义检索：ChromaDB 余弦相似度 (top-20)     │
│  3. 关键词检索：BM25 精确匹配 (top-20)         │
│  4. 加权 RRF 合并排序（语义 3 : BM25 1）      │
│  5. 返回 top-k 结果 + 预格式化引用             │
└──────────────┬───────────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────┐
│  ChromaDB (本地持久化)                        │
│  638 个预计算的条文向量                        │
│  每个向量附带元数据：法律名、章节、条号、日期    │
└──────────────────────────────────────────────┘
               │
               ▼
        JSON 结果返回给 Agent
        Agent 使用 citation 字段引用条号
```

### RAG（Retrieval-Augmented Generation）是什么

LLM 的知识来自训练数据，有两个固有缺陷：
1. **知识截止**：训练后发布的法律（如增值税法 2024.12.25）可能不在训练数据中
2. **幻觉**：LLM 可能编造不存在的条号或曲解条文内容

RAG 的解决方式：**先检索，再生成**。先从权威文本中找到相关条文，把原文塞进 LLM 的上下文窗口，让 LLM 基于原文回答。LLM 的角色从"凭记忆回答"变成"阅读理解"。

## 预处理流程（preprocess.py）

### 1. 文件名解析

```
中华人民共和国增值税法_20241225.md
        │                    │
        ▼                    ▼
  law_name              effective_date
  law_short_name = 增值税法（去掉"中华人民共和国"）
```

### 2. 正文提取

三类文档结构需要不同处理：

| 类型 | 文件 | 处理方式 |
|------|------|---------|
| 简单型 | 烟叶税法、车辆购置税法、契税法等 | 从第一个 `第X条` 开始 |
| 有目录 | 企业所得税法、关税法、税收征收管理法等 | 跳过 `目　　录` 块，从第二个 `第一章` 开始 |
| 条例型 | 增值税法实施条例等 | 从第一个 `第X章` 开始（无目录、无通过日期括注） |

目录必须跳过，否则会产生只含章节标题的无意义 chunks。

### 3. 按条分块（Article-Level Chunking）

核心正则：
```python
^(第[一二三四五六七八九十百零]+条)\s
```

**为什么按条分块而不是固定长度？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **按条分块**（本项目采用） | 保持法律引用的原子性；每块都是完整的法律条文；元数据（条号）精确 | 块大小不均匀（10-800字） |
| 固定长度（如 256 token） | 块大小均匀 | 可能切断一个条文；无法精确标注条号；破坏法律语义完整性 |
| 按章分块 | 上下文更丰富 | 块太大（几千字），embedding 稀释语义；检索精度下降 |

法律文本的最小引用单位是「条」。律师、会计师引用法律时说"根据第X条"，不会说"根据第X段"。按条分块直接对齐了用户的查询粒度。

### 4. Contextual Embeddings（Anthropic 方法）

这是提升检索精度的关键技术。对每个 chunk，用 LLM 生成 50-100 字的**上下文描述**，拼接在条文前面后再做 embedding。

**为什么需要？** 脱离上下文的条文可能语义模糊。比如"第一条　为了……制定本法"出现在所有 16 部法律中，纯条文的 embedding 几乎一样。上下文描述帮 embedding 模型区分不同法律的条文。

**示例：**
```
LLM 生成的上下文描述：
本条出自《中华人民共和国增值税法》第四章"税收优惠"，
规定了小规模纳税人的增值税起征点免征政策。
关键词：小规模纳税人、起征点、免征增值税、销售额。

原始条文：
第二十三条　小规模纳税人发生应税交易，销售额未达到起征点的，免征增值税…

拼接后用于 embedding：
[上下文描述] + [原始条文]
```

上下文描述使用 GPT-4.1-mini 生成，20 并发，638 chunks 约 1-2 分钟完成。

相比纯规则前缀 `【增值税法 第二章 税率】`，LLM 生成的上下文包含：
- 条文核心内容的通俗概括
- 关键检索词（同义词、近义词）
- 适用对象和场景

据 Anthropic 研究，Contextual Embeddings 可减少 **49%** 的检索失败率。

### 5. 附表处理

5 部法律有附表（税率表、当量值表等），以 `附：` 或 `附表X：` 开头。这些被切分为独立的 chunks，chunk_type 标记为 `appendix`。

### 6. 中文数字解析

条号（第七十二条）需要转为整数（72）用于排序和 ID 生成：
```
一 → 1,  十二 → 12,  二十 → 20,  七十二 → 72,  一百零一 → 101
```

## 混合检索原理（query.py）

### 为什么需要混合检索？

纯语义检索有盲区：

| 查询 | 语义检索 | BM25 关键词 | 混合检索 |
|------|---------|------------|---------|
| "增值税税率" | 找到第十条 | 找到第十条 | 找到第十条 |
| "第十条" | 找不到（无语义） | 精确匹配 | 找到 |
| "买东西要交多少税" | 找到（语义理解） | 找不到（无关键词） | 找到 |

### 检索流程

1. **语义检索**：将查询 embedding 后，在 ChromaDB 中做余弦相似度搜索，取 top-20
2. **BM25 检索**：基于中文 bigram 分词的关键词匹配，取 top-20
3. **加权 RRF 合并**：Reciprocal Rank Fusion，语义权重 3、BM25 权重 1

```python
# RRF 公式
rrf_score(doc) = Σ weight_i / (k + rank_i)
# k=60（常数），rank_i 是文档在第 i 个排序列表中的排名
```

语义权重更高（3:1）因为语义检索对自然语言查询更准确，BM25 作为补充处理精确关键词匹配。

### BM25 分词

使用简易中文 bigram 分词（无外部依赖）：
```
"增值税税率" → ["增值税税率", "增值", "值税", "税税", "税率"]
```

对 638 chunks 的小规模语料，bigram 足够有效，不需要 jieba 等分词库。

### 输出格式

每条结果自带预格式化引用，LLM 可直接使用：
```json
{
  "citation": "《中华人民共和国增值税法》第十条",
  "text": "第十条　增值税税率：（一）...",
  "chapter": "第二章 税率",
  "effective_date": "2024-12-25",
  "score": 0.0648
}
```

## 检索精度依赖什么

### 1. 分块粒度（最关键）

按条分块对齐法律引用的原子单位。所有条文都在 10-800 字之间，远低于 embedding 模型的 8191 token 上限。

### 2. Contextual Embeddings

LLM 生成的上下文描述是精度提升最大的单一因素。它让 embedding 能区分不同法律中的相似条文，并增加关键检索词覆盖。

### 3. 混合检索

语义 + BM25 互补：语义处理自然语言和同义表述，BM25 处理精确关键词和条号。加权 RRF 合并确保两种方法的优势都被利用。

### 4. 元数据过滤

`--law` 参数缩小搜索范围。在 638 chunks 中精确到某部法律（如增值税法 38 chunks），显著减少噪声。

### 5. Embedding 模型质量

当前使用 text-embedding-3-small（1536 维），对中文法律文本表现可用。更好的选择：
- **BGE-M3**：中文专优，支持稠密+稀疏+ColBERT 三种检索
- **GTE-Qwen2**：C-MTEB 排名最高
- 以上需要本地 GPU 或专门的 embedding API

> **重要：预处理和查询必须使用同一个 embedding 模型。** 不同模型的向量空间完全不同，维度、结构、距离度量都不可比。如果更换 embedding 模型（如从 text-embedding-3-small 换到 BGE-M3），必须用新模型重新运行 `preprocess.py` 重新生成所有 chunks 的 embedding，不能只改查询端。混用不同模型的向量会导致检索结果完全错误。

### 6. 查询质量

| 查询 | 检索效果 | 原因 |
|------|---------|------|
| "增值税税率" | 好 | 直接匹配 |
| "买东西要交多少税" | 好 | 语义检索理解意图 |
| "第十条" | 中等 | BM25 能匹配，但需配合 --law |
| "小规模纳税人月收入不超过10万要不要交增值税" | 好 | 语义丰富 |

## 已知局限

### 1. 未覆盖的法规

- 消费税（暂行条例，尚未立法）
- 资源税法
- 城镇土地使用税、房产税（暂行条例）
- 各类财政部/税务总局公告和政策文件

可通过添加 markdown 文件到 `docs/` 目录并重新运行 `preprocess.py` 来扩充。

### 2. 政策文件未覆盖

税法条文是框架性的，实际执行依赖大量政策文件（财政部/税务总局公告、国务院决定、总局解读）。这些文件数量多、变化快，本项目目前不涉及。

### 3. 纯条号查询效果有限

用户说"帮我看看第十条"——需要配合 `--law` 参数才能精确定位。BM25 能部分缓解这个问题。

### 4. 跨条文推理

有些问题需要综合多个条文。例如"小规模纳税人的增值税怎么算"涉及定义、标准、征收率、起征点等多条。top-k=5 通常能覆盖，但不保证。

### 5. 附表检索精度较低

附表是 markdown 表格，embedding 对表格内具体数值的匹配不如纯文本。"船舶吨税率表"能找到附表，但"超过10000净吨的船每年交多少税"可能找不到。

## 部署方式

### 本地预处理

```bash
# 安装依赖
pip install chromadb openai python-dotenv rank-bm25

# 配置 .env
echo "OPENAI_API_KEY=sk-xxx" > .env
echo "OPENAI_BASE_URL=https://openrouter.ai/api/v1" >> .env

# 运行预处理（分块 + contextual embedding + embedding）
python scripts/preprocess.py
# 输出：data/chunks.json（~28MB，638 chunks）
```

### 服务器部署

```bash
git clone https://github.com/zh00bc/law-rag.git
cd law-rag

# 安装依赖
pip3 install -r requirements.txt

# 导入预计算数据
python3 scripts/setup.py

# 复制到 OpenClaw workspace（不能用 symlink，会被安全机制拒绝）
cp -r . ~/.openclaw/workspace/skills/chinese-tax-law/

# 配置 .env（复用 OpenClaw 的 OpenRouter key）
echo "OPENAI_API_KEY=<your-key>" > ~/.openclaw/workspace/skills/chinese-tax-law/.env
echo "OPENAI_BASE_URL=https://openrouter.ai/api/v1" >> ~/.openclaw/workspace/skills/chinese-tax-law/.env

# 在 Telegram/微信中发 /new 开新 session
```

### 手动查询测试

```bash
python3 scripts/query.py --query "增值税的税率是多少"
python3 scripts/query.py --query "个人所得税税率" --top-k 3
python3 scripts/query.py --query "车辆购置税税率是多少"
python3 scripts/query.py --query "税务机关有哪些检查权力" --law 税收征收管理法
```

## 扩充法律

1. 将新的 markdown 文件放入 `docs/` 目录
   - 文件名格式：`中华人民共和国XXX法_YYYYMMDD.md`
   - 内容格式：标题 → 通过日期 → (可选目录) → 正文（第X条）
2. 重新运行 `python scripts/preprocess.py`（自动并发生成 contextual embedding）
3. 提交 `data/chunks.json` 和新的 `docs/` 文件
4. 服务器上重新导入 `python3 scripts/setup.py`

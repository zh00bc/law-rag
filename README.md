## 架构原理

```
用户提问
  │
  ▼
┌─────────────────────────────────────────────┐
│  OpenClaw Agent (kimi-k2.5 / DeepSeek / …)  │
│  识别为税法问题 → 调用 exec 工具             │
└──────────────┬──────────────────────────────┘
               │
               ▼
┌──────────────────────────────────┐
│  query.py                        │
│  1. 调用 OpenAI Embedding API    │
│     将问题转为 1536 维向量        │
│  2. 在 ChromaDB 中做余弦相似度   │
│     搜索，返回 top-k 条文        │
└──────────────┬───────────────────┘
               │
               ▼
┌──────────────────────────────────┐
│  ChromaDB (本地持久化)            │
│  310 个预计算的条文向量           │
│  每个向量附带元数据：              │
│  - 法律名、章节、条号、日期       │
└──────────────────────────────────┘
               │
               ▼
        JSON 结果返回给 Agent
        Agent 组织回答并引用条号
```

### RAG（Retrieval-Augmented Generation）是什么

LLM 的知识来自训练数据，有两个固有缺陷：
1. **知识截止**：训练后发布的法律（如增值税法 2024.12.25）可能不在训练数据中
2. **幻觉**：LLM 可能编造不存在的条号或曲解条文内容

RAG 的解决方式：**先检索，再生成**。先从权威文本中找到相关条文，把原文塞进 LLM 的上下文窗口，让 LLM 基于原文回答。这样 LLM 的角色从"凭记忆回答"变成"阅读理解"。

## 预处理流程（preprocess.py）

### 1. 文件名解析

```
中华人民共和国增值税法_20241225.md
        │                    │
        ▼                    ▼
  law_name              effective_date
  law_short_name = 增值税法（去掉"中华人民共和国"）
```

### 2. 正文提取

三类文档结构需要不同处理：

| 类型 | 文件 | 处理方式 |
|------|------|---------|
| 简单型 | 烟叶税法、船舶吨税法、印花税法 | 从第一个 `第X条` 开始 |
| 有目录 | 企业所得税法、关税法、增值税法、环保税法 | 跳过 `目　　录` 块，从第二个 `第一章` 开始 |
| 条例型 | 增值税法实施条例 | 从第一个 `第X章` 开始（无目录、无通过日期括注） |

目录必须跳过，否则会产生只含章节标题的无意义 chunks。

### 3. 按条分块（Article-Level Chunking）

核心正则：
```python
^(第[一二三四五六七八九十百零]+条)\s
```

**为什么按条分块而不是固定长度？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **按条分块**（本项目采用） | 保持法律引用的原子性；每块都是完整的法律条文；元数据（条号）精确 | 块大小不均匀（10-800字） |
| 固定长度（如 256 token） | 块大小均匀 | 可能切断一个条文；无法精确标注条号；破坏法律语义完整性 |
| 按章分块 | 上下文更丰富 | 块太大（几千字），embedding 稀释语义；检索精度下降 |

法律文本的最小引用单位是「条」。律师、会计师引用法律时说"根据第X条"，不会说"根据第X段"。按条分块直接对齐了用户的查询粒度。

### 4. 上下文前缀

每个 chunk 的文本前面加了前缀：
```
【增值税法 第二章 税率】
第十条　增值税税率：…
```

这不是装饰——它解决了一个关键问题：**脱离上下文的条文可能语义模糊**。比如"第一条　为了……制定本法"出现在所有 8 部法律中，如果不加前缀，embedding 会非常相似，检索时无法区分。前缀让 embedding 模型知道这是哪部法律的哪个章节。

### 5. 附表处理

4 部法律有附表（税率表、当量值表等），以 `附：` 或 `附表X：` 开头。这些被切分为独立的 chunks，chunk_type 标记为 `appendix`。附表通常是 markdown 表格，包含税率、税目等高频查询内容。

### 6. 中文数字解析

条号（第七十二条）需要转为整数（72）用于排序和 ID 生成：
```
一 → 1,  十二 → 12,  二十 → 20,  七十二 → 72
```

## Embedding 原理

### 什么是 Embedding

Embedding 将文本转为高维向量（本项目用 1536 维）。语义相近的文本在向量空间中距离更近。

```
"增值税的税率是多少"  →  [0.012, -0.034, 0.078, ...] (1536维)
"第十条 增值税税率：…" →  [0.015, -0.031, 0.082, ...] (1536维)
                                     ↑ 余弦相似度高
```

### 模型选择

本项目使用 **OpenAI text-embedding-3-small**（通过 OpenRouter 调用）：
- 维度：1536
- 最大 token：8191
- 成本：$0.02 / 1M tokens（310 chunks 总计约 $0.01）

对于中文法律文本，更好的选择可能是专门的中文 embedding 模型（如 BGE-M3、GTE-Qwen2），但需要本地 GPU。API 方案在便捷性和成本上更优。

### 非对称检索

注意：索引时和查询时的文本性质不同：
- **索引时**：文档原文（陈述句，如"增值税税率为百分之十三"）
- **查询时**：用户问题（疑问句，如"增值税的税率是多少"）

text-embedding-3-small 对此有内在处理，不需要额外的查询前缀。但如果换用 BGE 系列模型，查询时必须加前缀 `"为这个句子生成表示以用于检索相关文章："`。

## 检索精度依赖什么

### 1. 分块粒度（最关键）

分块粒度决定了检索的"分辨率"。

- **太粗**（按章）：用户问"增值税税率"，返回整章 20 多条，LLM 需要自己在长文本中找答案，效率低且可能遗漏
- **太细**（按句）：一个条文的多个款项被拆散，丢失完整语义。如"第四条 企业所得税的税率为25％"和"非居民企业…适用税率为20％"被拆成两个 chunk，检索时可能只命中一个
- **刚好**（按条）：每个 chunk 是一个完整的法律条文，既保持语义完整性，又足够精确

本项目所有条文都在 10-800 字之间，远低于 embedding 模型的 8191 token 上限，不需要二次切分。

### 2. 元数据过滤

ChromaDB 支持按元数据过滤。用户问"增值税法的税率"时，`--law 增值税法` 参数可以把搜索范围限制在 38 个 chunk 内，避免被其他法律的相似条文干扰。

没有过滤时的典型问题：
- "税率是多少" → 可能同时返回增值税法、企业所得税法、关税法的税率条文
- 这在某些场景下是优势（综合查询），但在精确查询时是噪声

### 3. Embedding 模型质量

影响维度：
- **中文理解能力**：模型是否能准确捕捉中文法律术语的语义（如"纳税人"vs"扣缴义务人"）
- **语义区分度**：相近但不同的概念是否有足够的向量距离（如"免征"vs"减征"vs"不征"）
- **跨表述匹配**：用户口语化提问能否匹配到正式法律用语（如"免税"能否匹配到"免征增值税"）

text-embedding-3-small 对中文法律文本的表现实测可用，但不是最优。专门的中文模型（BGE-M3、GTE-Qwen2）在中文语义细粒度上更好。

### 4. 查询质量

用户的提问方式直接影响检索效果：

| 查询 | 检索效果 | 原因 |
|------|---------|------|
| "增值税税率" | 好 | 直接匹配条文关键词 |
| "买东西要交多少税" | 中等 | 口语化，与法律用语有语义差距 |
| "第十条" | 差 | 纯条号，没有语义信息 |
| "小规模纳税人月收入不超过10万要不要交增值税" | 好 | 虽然长，但语义丰富，能匹配到起征点条文 |

### 5. top-k 参数

- **top-k 太小**（如 1-2）：可能遗漏相关条文。法律问题往往涉及多个条文（如税率+优惠+征管）
- **top-k 太大**（如 20+）：引入大量不相关内容，LLM 上下文被稀释，可能"捡芝麻丢西瓜"
- **推荐值 5-10**：对大多数税法问题足够覆盖

### 6. 距离度量

本项目使用余弦相似度（cosine similarity）：
```
similarity = 1 - cosine_distance
```

范围 0-1，越接近 1 越相似。实测中：
- 0.65+ ：高度相关，通常是正确条文
- 0.55-0.65：相关，可能是关联条文
- 0.50 以下：通常不相关

## 已知局限

### 1. 未覆盖的法律

以下常见税法**未收录**：
- 个人所得税法（含实施条例）
- 税收征收管理法（含实施细则）
- 车辆购置税法
- 消费税（暂行条例，尚未立法）
- 资源税法
- 城市维护建设税法
- 契税法
- 耕地占用税法
- 城镇土地使用税、房产税（暂行条例）

可通过获取对应 markdown 文件放入 `docs/` 目录，重新运行 `preprocess.py` 来扩充。

### 2. 政策文件未覆盖

税法条文是框架性的，实际执行依赖大量政策文件：
- 财政部/税务总局公告（如小规模纳税人优惠政策）
- 国务院决定
- 总局解读

这些文件数量多、变化快，本项目目前不涉及。

### 3. 纯条号查询无效

用户说"帮我看看第十条"——embedding 无法仅从条号推断语义。需要配合 `--law` 参数才能定位。

### 4. 跨条文推理

有些问题需要综合多个条文才能回答。例如"小规模纳税人的增值税怎么算"需要同时参考第八条（小规模纳税人定义）、第九条（标准）、第十一条（征收率）、第二十三条（起征点）。top-k=5 通常能覆盖，但不保证。

### 5. 附表检索精度较低

附表（税率表、当量值表）是 markdown 表格，embedding 对表格结构的理解不如纯文本。用户问"船舶吨税率表"能找到附表，但问"超过10000净吨的船每年交多少税"可能找不到，因为 embedding 难以精确匹配表格内的具体数值。

```
law-rag/
├── SKILL.md                  # OpenClaw skill 定义
├── README.md                 # 本文档

├── setup.sh                  # 服务器一键安装脚本

├── scripts/
│   ├── preprocess.py         # 本地运行：解析→分块→embedding→导出 JSON
│   ├── query.py              # 服务器运行：语义检索，输出 JSON
│   └── setup.py              # 服务器运行：从 JSON 导入 ChromaDB
├── data/
│   └── chunks.json           # 预计算数据（310 chunks + 1536维 embedding，~13MB）
├── docs/

```

## 部署方式

### 本地预处理

```bash
# 安装依赖
pip install chromadb openai python-dotenv

# 配置 .env
echo "OPENAI_API_KEY=sk-xxx" > .env
echo "OPENAI_BASE_URL=https://openrouter.ai/api/v1" >> .env

# 运行预处理（解析+分块+embedding）
python scripts/preprocess.py
# 输出：data/chunks.json（~13MB，310 chunks）
```

### 服务器部署

```bash
git clone https://github.com/zh00bc/law-rag.git
cd law-rag

# 安装依赖
pip3 install chromadb openai python-dotenv

# 导入预计算数据
python3 scripts/setup.py

# 复制到 OpenClaw workspace（不能用 symlink）
cp -r . ~/.openclaw/workspace/skills/chinese-tax-law/

# 配置 .env（复用 OpenClaw 的 OpenRouter key）
echo "OPENAI_API_KEY=<your-key>" > ~/.openclaw/workspace/skills/chinese-tax-law/.env
echo "OPENAI_BASE_URL=https://openrouter.ai/api/v1" >> ~/.openclaw/workspace/skills/chinese-tax-law/.env

# 重启 gateway + 新 session
# 在 Telegram/微信中发 /new
```

### 手动查询测试

```bash
python3 scripts/query.py --query "增值税的税率是多少"
python3 scripts/query.py --query "企业所得税率" --top-k 3
python3 scripts/query.py --query "哪些情形免征关税" --law 关税法
```

## 扩充法律

1. 将新的 markdown 文件放入 `docs/` 目录
   - 文件名格式：`中华人民共和国XXX法_YYYYMMDD.md`
   - 内容格式：标题 → 通过日期 → (可选目录) → 正文（第X条）
2. 重新运行 `python scripts/preprocess.py`
3. 提交 `data/chunks.json` 和新的 `docs/` 文件
4. 服务器上 `git pull` 后重新运行 `python3 scripts/setup.py`
